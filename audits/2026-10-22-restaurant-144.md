# Restaurant assessment and fixes — 22 October 2026

The main blocker is incomplete operational setup. The application already shares a menu across the public site and POS, supports ingredient costing, records preparation and waste, captures sales and has promotion analysis. The active customer menus are not yet connected to usable serving recipes and opening stock. More charts alone cannot resolve that gap.

| Area | Verified state | Implication |
| --- | --- | --- |

Inactive development recipes were not reactivated or guessed. No menu prices, recipe quantities, opening stock, sales or user permissions were invented.

## Changes shipped in release 144

### Setup and layout

- Added **Overview → Setup & connections → Check setup**. The check reports menu readiness, stock needing attention and receipt coverage, with searchable issue lists and direct links to recipe, ingredient and stock-entry forms.
- Setup checks cover missing recipe quantities, unresolved recipe notes, circular/broken bundles, unavailable ingredients, missing ingredient costs, unit reviews, currency mismatches, missing stock conversions, unconfigured customization portions and pending POS approval.
- The setup panel explains the actual connections and the manual online-order and Accounting boundaries.
- Results use compact phone cards and an expandable issue list so dozens of setup rows do not bury daily actions. Existing navigation, branding, operational tables and login styling remain intact.
- The check runs only when requested, uses one compact database call, and transfers no photos or movement-history rows. It does not hold up login.

### Loading and consistency

- Opening ordinary Menu screens no longer downloads either Inventory movement history or POS deduction history. Inventory and stock-dependent Kitchen/Integration workflows still fetch complete paginated ledgers. Concurrent requests that need stock upgrade a pending catalog-only load correctly.
- The homepage receipt graph now calls the paginated receipt endpoint directly; viewing a report no longer downloads the cashier/offline module (about 76 KB of uncompressed JavaScript).
- A small invalidation coordinator marks dependent reports/catalogs stale after acknowledged catalog, POS, public-menu and Kitchen writes. Same-browser tabs exchange only invalidation scopes, never private records. Unsaved forms are retained; returning to Sales refreshes stale data, while active reports prompt for refresh.
- Late catalog/report responses are cancelled or invalidated after relevant changes so an old read cannot replace newer data.
- Public website navigation and menu rendering no longer wait for the live-menu request. A recent validated public cache, or the existing published fallback, renders immediately while prices are checked. Checkout waits for that check, and basket prices/availability are reconciled with the live response. Empty live menus remain empty.
- Existing offline POS and Kitchen capture queues were preserved. This change does not promise live cross-device updates while disconnected or remove the need for the first authenticated connection.

### Database cleanup

- Added `restaurant_readiness144()` as a read-only, SECURITY INVOKER function, with an explicit administrator guard and existing table RLS. Anonymous execution is denied.
- Removed two duplicate stock indexes while retaining the identical covering indexes.
- Changed the membership policy's user-ID check to an initplan-compatible `SELECT auth.uid()` expression, preserving its authorization rule.
- Post-install advisors no longer report duplicate indexes or the per-row auth check. Existing uncovered foreign keys, overlapping policies and unused indexes were not indiscriminately changed: they were not established bottlenecks for this workload. Existing guarded RPC notices and disabled leaked-password protection remain. [Supabase index guidance](https://supabase.com/docs/guides/database/database-linter?lint=0009_duplicate_index), [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security#call-functions-with-select), [password-protection guidance](https://supabase.com/docs/guides/auth/password-security).

These are feature/workflow comparisons, not a claim that this custom application has every capability or service guarantee of Square or Toast.

## Next operational steps, in order

1. Enter serving quantities for the 34 active menus. Customizable meals also need portions for sauces, vegetables, proteins and included drinks, or an explicitly verified no-stock option where appropriate.
2. Confirm batch yields, conversions and any remaining development recipe notes before activating those recipes.
3. Count real on-hand inventory and record opening stock. Do not use assumed quantities merely to make POS accept a payment.
4. Review recipes/links, approve each POS item, open a shift and use the normal payment workflow for actual sales. Refunds, preparation and waste should use their dedicated workflows.
5. Keep fees, packaging, overhead and capital assumptions current. Actual accounting profit requires expense integration or reconciliation with Accounting.

Further product work should follow operating needs: native online-order intake and a kitchen ticket queue, supplier purchase orders and receiving, physical-count variance, and an explicit restaurant-to-Accounting reconciliation. These were not silently added because they introduce new customer, staff and accounting workflows beyond correcting the current foundations. Foodpanda orders are not automatically imported.
