# Customer website review and Word of Hope integration

The legacy `/web/` URL redirects to `/Restaurant-Back-Office/public-restaurant/`.
The live Home, Menu, Words of Hope and Reviews screens were inspected on 26 October 2026.

## Design and workflow findings

- The green branding is consistent, but small muted descriptions and subtle borders reduce readability.
- The home hero occupies substantial space before food, hours, directions or an ordering action. Put these practical actions first and shorten the About section.
- Menu photos are small and French Fries uses a placeholder. Use consistent food photography and stronger product/price/action hierarchy.
- Menu categories exist, but a search field and useful dietary/allergen information would help customers find suitable dishes. Confirm ingredient claims with the restaurant before publishing them.
- Orders are handed off through WhatsApp or Messenger. Make the remaining send and restaurant-confirmation steps prominent; opening a messaging app does not place an accepted order.
- The reviews carousel exposes repeated copies in the accessibility tree. Make the duplicate animation content hidden from assistive technology and offer pause/static reading.
- The old Word of Hope Apps Script request used `no-cors`, so the site could not verify delivery.

## Implemented scope

- Replaced Word of Hope submission with an acknowledged Edge Function save and private shared inbox.
- Added `Word of Hope` to the existing Journal / HR workbook, with retained sharing permissions.
- Preserved public drafts, added stable retry IDs, explicit delivery feedback, optional permission to feature, and character-based validation suitable for Lao input.
- Added admin notification bell entries and an inbox link in both Restaurant and Accounting. Read receipts are recorded after message content appears, separately for each account and app. Opening the bell/list does not mark messages read.
- Polls active apps approximately every 30 seconds and refreshes on focus/reconnection. These are in-app notifications, not device push notifications while apps are closed.
- Uses the existing Accounting Google connection. Messages are durable before spreadsheet delivery; scheduled retries recover pending copies. The spreadsheet receives RAW strings so customer text cannot become a formula.
- Existing historic Apps Script submissions and the rest of the public-site design were not migrated or redesigned.

## Verification

- Live public endpoint: one temporary test submission sent twice returned the same ID and produced exactly one database record and one spreadsheet row. Test data was removed after verification.
- Database transaction tests: retry idempotency, independent Accounting/Restaurant read receipts, and denied direct client access.
- Public endpoint rejected unauthenticated inbox reads for both apps, unauthorized sync and malformed submissions; CORS verified.
- DOM tests: Lao input, retained draft, duplicate clicks, same-ID retry, confirmed success, read receipt after content display, escaping and logout cleanup.
- Existing public storefront runtime suite: nine checks passed.
- Accounting module build, source ownership and approved-byte structural checks passed after recording this authorized change.
- Supabase security advisor: no findings naming the new inbox objects.
- Signed-in visual verification of both admin apps was not performed; notification interactions were verified with the actual client module in DOM tests and database access tests.

The broader visual improvements above are recommendations for a separate design pass.
